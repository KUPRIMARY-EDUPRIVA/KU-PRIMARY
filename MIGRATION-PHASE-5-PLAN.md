# Phase 5 — unified Supabase tenant, app and chatbot cutover

## Confirmed target

- One Supabase project serves KU, Kiwanja and future schools.
- One Supabase Auth identity can hold multiple school memberships. After login,
  the app loads memberships for that authenticated UUID and allows switching
  only among those schools.
- `source_project` remains data provenance, not a school authorization
  boundary. Existing values remain `ku` and `kiwanja`; new-school records use
  an additional `platform` provenance value. Every business query remains
  scoped to a globally unique `school_id` as well as provenance.
- Chatbot data access uses a server-side allowlisted query/action registry
  under the authenticated caller's RLS. No service-role data queries and no
  school/student data is sent to an external AI provider.
- Kiwanja's legacy Firebase password parameters are reported as configured
  server-side. Do not copy them into the app or repository.

## Read-only identity profile

The current Supabase Auth mapping contains 49 KU and 13 Kiwanja identities.
The profile showed no overlapping emails or Auth UUIDs across sources, and the
two current source memberships cover one school each (43 KU users, 11
Kiwanja users; 54 memberships total). No cross-source school-ID collision
was found. These are aggregate counts only; no email, name, or student record
was read for this check.

This means the existing 62 Auth identities can remain distinct at initial
cutover. The membership model must nevertheless support multiple schools for
one UUID going forward. If a person needs their existing accounts combined,
linking must verify both credentials before changing the account; email match
alone is insufficient.

## Required implementation phases

### 5A. Tenant and provisioning schema

Prepare additive SQL and tests to:

1. Add `platform` as an allowed provenance value to source-constrained Auth,
   membership, Phase 2 imported-data, and Phase 4 active-flow relations. Do
   not rewrite existing `ku`/`kiwanja` provenance values.
2. Replace the current one-membership-per-source key with a
   `(auth_user_id, source_project, school_id)` membership key and index for
   school/user lookup. Preserve all existing memberships and self-read RLS;
   mutations remain server-only.
3. Add a globally unique school identity/registry contract for future school
   provisioning. New school IDs must be generated by the trusted provisioning
   function, never accepted as authorization from the browser.
4. Keep school creation, admin assignment, invitation, membership changes and
   school switching fail-closed. No public sign-up or client role assignment.

The DDL must preflight exact current constraints, preserve rows, run in one
transaction, and verify all current memberships and row counts remain intact.
It must not broaden app table grants or import data. Present the exact SQL and
dry-run checks for review before any production apply.

### 5B. Unified Auth and school context

1. Replace the `REACT_APP_AUTH_MIGRATION_SOURCE=ku|kiwanja` app pin with a
   single Supabase Auth client configuration.
2. On sign-in, first attempt the existing Supabase password. For legacy
   users, a rate-limited server function resolves exactly one source-scoped
   Auth mapping by normalized email and verifies against that source's
   server-held Firebase scrypt parameters. Ambiguous source mappings fail
   closed. It must not overwrite an Auth password when linking another
   source; that requires proof of both legacy credentials.
3. Load memberships for `auth.uid()` from a self-readable membership relation.
   The app may select an active school only from those returned rows. The
   active membership supplies school and role for display; policies remain
   the authority.
4. Provision new schools and accounts only through an authenticated,
   role-checked server workflow; no service-role key reaches the client.

### 5C. Database policies and repositories

- Review Phase 2 imported parent and child tables as a separate RLS matrix.
  Phase 2's current grants are not a complete app authorization policy.
- Recheck Phase 4 policies against the unified school-membership model. Keep
  the eleven relations listed in `MIGRATION.md` denied until each blocker is
  resolved.
- Migrate domain repositories in small groups (school/profile, students and
  teachers, results, attendance, fees/payments, then remaining modules).
  Every query uses the authenticated Supabase session and tenant predicates;
  SQL policies enforce the same source/school/role boundaries independently.
- Add negative tests for another school, another provenance, unauthorized
  role, teacher outside assigned classes/subjects, and student self-access.
- Do not remove Firebase from any module until equivalent read/write,
  reporting, realtime and failure behavior has passed.

### 5D. Role-aware school assistant

The current LABAN chatbot is a deterministic keyword router with a limited
set of intents. It reads students/counts/class-teacher data directly from
Firestore, calls Firebase-Admin Netlify functions for performance and school
facts, and contains a UI-only role check for daily collections. This cannot
answer the whole system safely or reliably after Firebase is retired.

Replace it with a registry of explicit question/report tools. Each tool must
declare its table/query, required filters, allowed roles, output fields,
whether it returns aggregate or record-level data, and whether user
confirmation is required. Initial domains:

| Domain | Example questions | Role/data guard |
|---|---|---|
| School profile and CBC/CBE setup | school details, levels, classes, learning areas, terms | Same-school membership; expose only configured school facts |
| Students and staffing | counts, class roster, class teacher, authorized student profile | Same-school role; teachers limited to assigned class/learning areas |
| Results and reports | class mean, learning-area trends, ranking, report completeness | Results RLS and teacher assignment; named student results only for roles allowed to see them |
| Attendance | daily/monthly rates, class summaries, individual attendance | Same role/class/learner boundary as attendance pages |
| Finance | balances, invoices, collections and M-Pesa status | Fee-manager rules; student/parent sees only verified own records |
| Discipline, health, boarding, transport | status and summaries | Restricted roles and minimum necessary fields; student/parent ownership verified |
| Timetables and operations | today's timetable, duties and events | Same-school membership; teacher view limited to own assignments |
| System help | how to use modules, CBC/CBE guidance, support | Static approved product and curriculum knowledge, separate from private records |

Natural-language routing can map questions to these tools, but the model must
never generate arbitrary SQL or decide authorization. The server validates
the tool, derives identity and school from the verified Supabase session, and
lets RLS enforce access. Chat caches must include user/membership scope, query
filters and data version; no cross-user cached PII. Payments, SMS and record
changes require explicit confirmation and invoke the existing trusted
business function rather than an LLM-generated action.

### 5E. Data parity, cutover and cleanup

- Reconcile Firebase source counts against each imported Postgres relation by
  source and school, including normalized child cardinalities. Historical
  source snapshots remain available for rollback; do not overwrite or drop
  source data.
- For any missing records, prepare a source-fixed, idempotent import plan and
  show the row-count/child-count report before import approval.
- Run end-to-end auth, multi-school isolation, role authorization, report,
  payment callback, offline-queue and reconnect tests.
- Cut one workflow at a time behind an explicit backend switch. Roll back by
  switching that workflow to Firebase; retain Firebase data until parity and
  user acceptance are confirmed.
- Remove Firebase client packages, Firebase config, native Google Services
  config, and Firebase Admin integrations only after no shipped path depends
  on them. Keep any still-required server integrations until their replacement
  is validated.

## Current blockers and next gate

The existing migration branch has only a transitional staff-login shadow
session. It still signs into Firebase first; Firebase remains the app's
identity for data and the offline queue replays Firestore operations. Thus it
is not a Supabase cutover. The current `.env.local` also pins the shadow
session to `ku`; the shared-login design must remove that app-level source
pin. The Phase 2 relation grants, profile/session migration, provisioning,
and data repositories still need implementation.

The next step is **5A schema preparation only**: author an additive,
transactional, tested SQL proposal and verification script; do not apply it
until the exact DDL is reviewed and approved. No imports, data changes, new
policies, or Firebase cutover are authorized by this planning document.
